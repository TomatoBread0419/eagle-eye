# 🔄 工作流设计

## 概述

Eagle Eye 的工作流设计遵循 **"AI 做判断，代码做执行"** 的核心原则。一个完整的工作流包含三个阶段：**感知 → 判断 → 执行**。

---

## 工作流全景

```
┌────────────────────────────────────────────────────┐
│                  感知阶段 (Sense)                    │
│  定时触发 → 数据采集 → 市场扫描 → 信号生成          │
└────────────────────┬───────────────────────────────┘
                     │
┌────────────────────▼───────────────────────────────┐
│                  判断阶段 (Judge)                    │
│  信号评估 → 候选筛选 → 仓位计算 → 风控验证          │
└────────────────────┬───────────────────────────────┘
                     │
┌────────────────────▼───────────────────────────────┐
│                  执行阶段 (Execute)                  │
│  订单生成 → 状态机流转 → 提交执行 → 审计记录         │
└────────────────────────────────────────────────────┘
```

---

## 阶段一：感知 (Sense)

### 触发方式

| 触发类型 | 示例 | 精度 |
|----------|------|------|
| **Cron 定时** | 每日 08:00 运行 GARP 扫描 | ±1 分钟 |
| **事件驱动** | 用户通过 WeChat 发送查询指令 | 即时 |
| **自触发** | 前一个工作流输出作为后一个的输入 | 串行 |

### 数据采集

```
定时触发
  ↓
并行拉取 3 个数据源：
  ├─ Alpaca API → 当前持仓、账户权益、挂单状态
  ├─ 腾讯行情   → 87 只候选池实时报价
  └─ 市场新闻   → WallStreetCN + 搜狗微信 + Google News
  ↓
数据去重、标准化、缓存（60秒 TTL）
```

### 市场扫描

扫描器 `us_screener.py` 对 87 只候选池进行 13 维度评分：

```
评分维度：
  1. 动量（5日/20日/60日）
  2. 相对强度（vs SPY）
  3. RSI（14日）
  4. 成交量异常
  5. 波动率（ATR %）
  6. 板块事件偏置
  7. beta 系数
  8. PE 估值
  9. 股息率
  10. 距离支撑/阻力位
  11. 机构持仓变化
  12. 分析师评级调整
  13. AI 叙事热度
```

输出：`top 5-8 候选列表（含评分和理由）`

## 阶段二：判断 (Judge)

### AI 决策流程

这是整个系统的核心。AI Agent 接收扫描结果，形成独立判断。

```
输入：扫描器输出的候选列表 + 市场事件报告 + 当前持仓
  ↓
Step 1: 市场环境评估
  AI 判断当前市场模式：
  - 趋势市 / 震荡市 / 风险市
  - 板块轮动方向
  - 宏观事件影响
  ↓
Step 2: 持仓再平衡
  AI 检查当前持仓是否健康：
  - 各板块配置是否偏离 target
  - 各持仓距止损线距离
  - 是否需轮出/轮入
  ↓
Step 3: 候选筛选
  从扫描器输出的 top 5-8 候选中：
  - 排除近期止损过的股票（用户反感"反复横跳"）
  - 排除龙头股（#1-#2 跳过，选 #3-#5）
  - 偏好中小盘高成长（用户投机风格）
  ↓
Step 4: 仓位计算
  AI 综合评估后决定：
  - 目标仓位（基于凯利公式 + AI 判断调节）
  - 单只限制 3-20%（大盘）或 ≤10%（小盘）
  - 板块限制 ≤30%
  ↓
Step 5: 风控验证 (Policy Validator)
  硬约束检查：
  - ✅ 单只 ≤ 18%
  - ✅ 板块 ≤ 30%
  - ✅ 总暴露 ≤ 90%
  - ✅ 活跃持仓 ≥ 6
  - ✅ 候选通过 2-3 个周期确认
  ↓
输出：OrderIntent（订单意图 JSON）
```

### AI 判断 vs 规则引擎

| 方面 | 传统量化 | Eagle Eye (AI 驱动的) |
|------|----------|----------------------|
| **评分** | 固定权重公式 | AI 综合评估所有维度 |
| **过滤** | 硬编码条件 | AI 根据市场环境动态调整 |
| **仓位** | 固定公式 | AI + 凯利双重计算 |
| **例外处理** | 无法处理 | AI 可以解释为什么破例 |

## 阶段三：执行 (Execute)

### 订单生命周期

```
OrderIntent (AI 生成)
  ↓
PENDING — 订单创建
  ↓
VALIDATING — 验证阶段
  ├─ Policy Validator（风控铁律）
  ├─ 降级模式检查（系统是否异常）
  └─ 双签名规则（>=2 信号才执行卖出）
  ↓
APPROVED — 通过验证
  ↓
SUBMITTED — 提交到 Alpaca
  ↓
FILLED — 成交
  ↓
COMPLETED — 结算确认
  │
  └→ 如果 FAILED / CANCELLED：
     AI 记录失败原因，放入重试队列
     或生成替代方案
```

### 止损管理

```
新持仓建立
  ↓
自动挂止损单（基于 ATR + AI 调整）
  │
  ├─ 价格触发止损 → 自动卖出
  │     ↓
  │   60 分钟内 AI 寻找替代买入机会
  │
  └─ 价格远离止损 → 止损线上移（保护利润）
```

### 审计日志

每个操作都生成不可篡改的审计记录：

```json
{
  "action": "SELL",
  "ticker": "ARM",
  "shares": 5,
  "price": 127.50,
  "rationale": "止损触发：股价跌破MA20+板块情绪转弱",
  "policy_checks": [
    {"rule": "max_position", "pass": true},
    {"rule": "sector_limit", "pass": true}
  ],
  "agent_version": "deepseek-v4-flash",
  "timestamp": "2026-06-24T21:35:00+08:00"
}
```

## 完整工作流示例：每日开盘检查

### 触发时间
BJT 21:00-22:00（US 市场开盘）

### 流程

```
21:00 — Cron 触发
  ↓
21:01 — AI 读取所有状态为 "new" 的挂单
  ↓
21:02 — 板块感知审核
  ├─ 计算各板块当前占比
  ├─ 识别缺配板块（如半导体仅 25% vs 目标 35%）
  └─ 标注"唯一持仓"的限售规则
  ↓
21:03 — 撤销不合理卖单
  └─ 缺配板块的唯一持仓不卖
  ↓
21:04 — 扫描器运行
  └─ 输出今日候选列表
  ↓
21:05 — AI 判断是否需要补仓
  ├─ 确认候选、计算仓位
  └─ 生成 OrderIntent
  ↓
21:06 — Policy Validator 验证
  ↓
21:07 — 提交订单 + 审计日志
  ↓
21:08 — WeChat 推送开盘检查报告
```

## 异常工作流

### 场景：API 不可用

```
Alpaca API 超时（×3 重试后）
  ↓
系统进入降级模式
  ├─ 所有交易动作暂停
  ├─ 从缓存读取最近一次持仓快照
  └─ 输出"降级模式"报告
  ↓
15 分钟后自动重试
  ├─ 恢复 → 退出降级模式
  └─ 仍不可用 → 继续降级，记录告警
```

### 场景：DNS 劫持

```
qt.gtimg.cn 返回 198.18.0.x（劫持 IP）
  ↓
sitecustomize.py 检测劫持
  ├─ 自动回退 Google DoH 重解析
  ├─ 缓存正确 IP
  └─ 继续正常请求（对应用层透明）
```

## 工作流设计原则

1. **幂等性** — 同一工作流重复执行不会产生副作用
2. **可恢复** — 任何阶段崩溃都可以从上次恢复点重试
3. **可审计** — 每个工作流的每个步骤都有日志记录
4. **降级优先** — 无法执行完整流程时，一定有降级方案
5. **最少人工干预** — AI 自主处理 99% 的情况，只有边界问题才通知用户
