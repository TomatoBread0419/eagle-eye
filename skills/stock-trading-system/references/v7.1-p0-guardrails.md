# V7.1 P0 Guardrails — Hard Policy Enforcement

**Date:** 2026-06-18
**Purpose:** Move from "LLM reads policy and self-enforces" to "code-level hard gates."

## Architecture

Before P0:
```
LLM reads policy doc → LLM decides to follow or not → trade_executor → Alpaca
```

After P0:
```
LLM generates OrderIntent
  ↓
Gate 0: Dashboard exists? (§7) → REJECT ALL if missing
  ↓
Gate 1: Active Sectors (§5) → <4 → check §6.1 Seed
  ↓
Gate 2: Candidate Confirmation (§6) → scan_count ≥ 2, seed exempt
  ↓
Gate 3: Exposure (§5) → pos≤18%, sector≤30%, total≤90%
  ↓
PASS → Safety Check → OMS → Alpaca
REJECT → policy_violations log → skip
```

## The PASS/REJECT Pattern

All three guardrails follow the same contract:
- **Input:** OrderIntent + portfolio state snapshot
- **Output:** (bool, str) — PASS or REJECT with reason
- **No side effects:** Never generates trade suggestions, never modifies orders
- **No AI:** Pure rule evaluation, no LLM involved

This pattern is reusable for any future policy rules.

## Files

| File | Purpose |
|------|---------|
| `eagle_eye/risk/policy_validator.py` | Core validation engine (6 check functions) |
| `eagle_eye/execution/candidate_tracker.py` | Multi-cycle scan tracking (SQLite) |
| `eagle_eye/storage/models.py` | +`candidate_history` + `policy_violations` tables |
| `eagle_eye/execution/trade_executor.py` | `execute_mode()` wired to all 3 gates |

## Key Design Decision

The policy_validator is called inside `execute_mode()`, NOT in a separate pre-check step. This means:
- Every OrderIntent that reaches Alpaca has been validated
- Impossible to bypass by calling a different code path
- Validation happens at the last possible moment (with live portfolio state)

## Learned: Policy Document vs Code Enforcement Gap

The V7.1.1 lesson: writing a policy document (auto_approval_policy.md) is not enough.
Without code-level enforcement, the system relies on LLM "self-discipline."
The correct sequence is:
1. Write policy document (owner-approved constraints)
2. Implement code-level gates (PASS/REJECT, no exceptions)
3. Wire gates into the execution pipeline (single choke point)
4. Test with dry runs (mock broker, known inputs → expected outputs)
