# V7.1 Production Audit Patch — Patterns & Pitfalls

**Date: 2026-06-18**
**Context: Post-Phase 5 production audit fixing code quality issues**

---

## Pattern 1: HTTP Bypass Removal

**Problem**: Raw `urllib.request` calls in execution and strategy layers bypass the approved broker isolation (Constitution #6: Broker isolated).

**Fix**: Replace all direct urllib calls with approved clients:
- Alpaca API calls → `broker/alpaca_client.place_order()` (or `get_alpaca_client()` singleton)
- External HTTP calls → `core/http.http_get()` / `http_post()`

**Files affected**:
- `execution/trade_executor.py`: Hard-constraint buy block replaced raw urllib POST with `_ac.place_order()`
- `strategy/market_env.py`: FRED data fetch replaced `urllib.request.urlopen()` with `http_get()`

**Verification**: `grep -rn 'urllib' eagle_eye/execution/ eagle_eye/strategy/` should return nothing.

## Pattern 2: Duplicate Audit Table Resolution

**Problem**: Two independent audit tables created by separate modules:
- `audit_logs` (plural, from `storage/models.py`) — used by `AuditLogRepo`
- `audit_log` (singular, from `ops/audit_engine.py`) — used by audit engine + behavior_fingerprint

**Fix**:
1. Choose canonical: `audit_log` (richer schema: severity, source, user_notified)
2. Add missing column: `ALTER TABLE audit_log ADD COLUMN action TEXT`
3. Update `AuditLogRepo` to write to `audit_log` with all fields
4. Remove `audit_logs` from `models.py` CREATE_TABLES and indexes
5. Old `audit_logs` table becomes orphaned (no code writes to it, existing data preserved)

**Pitfall**: Existing database already has `audit_log` without the `action` column. Must ALTER TABLE before new code runs. The `CREATE TABLE IF NOT EXISTS` in audit_engine won't add new columns to existing tables.

## Pattern 3: Monolithic Repository Split

**Problem**: `storage/repositories.py` at 516 lines — above target, hard to navigate.

**Fix**: Split into submodules under `storage/repos/`:
- `positions.py` — PositionRepo, RiskStateRepo
- `watchlist.py` — WatchlistRepo
- `calibrated.py` — CalibratedParamsRepo
- `market.py` — RegimeRepo, MarketEnvRepo, SignalDecayRepo
- `history.py` — TradeHistoryRepo, ComplianceRepo
- `pending.py` — PendingReplacementRepo, RecentStopRepo
- `system.py` — AuditLogRepo, HealthCheckRepo, SchedulerJobRepo, ConfigStoreRepo

Original `repositories.py` becomes a thin re-export module (30 lines) that imports from all submodules. Backward compatible: all existing `from eagle_eye.storage.repositories import XXX` continue working.

**Rule**: Each submodule should stay under 100 lines.

## Pattern 4: sys.path Removal

**Problem**: `main.py` and `storage/migrate.py` use `sys.path.insert()` to make `eagle_eye` package importable. This is fragile and non-standard.

**Fix**: Remove `sys.path.insert()` calls. Project requires `PYTHONPATH` set to project root:
```bash
PYTHONPATH=$HOME python3 eagle_eye/main.py health
```
Or run as module:
```bash
cd ~ && python3 -m eagle_eye.main health
```

**Checklist when removing sys.path**:
- Verify `import sys` is still needed (e.g., `sys.exit` in main.py)
- If `import sys` was only for `sys.path`, remove the import entirely
- Test with `PYTHONPATH=~/ python3 eagle_eye/main.py health`

## Pattern 5: Behavior Parity Report Methodology

**Anti-pattern**: Report "100% parity because V7 bridges to V6 via subprocess." This hides real gaps.

**Correct approach**: Compare V7 **native** modules against V6 on identical snapshots:
- Native = V7 code runs directly, no subprocess bridge
- Score each category independently: Signals, Buy List, Sell List, Kelly, Exposure, OrderIntent, Execution
- Report honest percentages with specific gap identification

**Example from 2026-06-18 audit**:
- Signals: 85% native (screener not migrated)
- Buy List: 50% native (candidate generation not migrated)
- Sell List: 100% native
- Kelly: 100% native
- Overall weighted: 83%
