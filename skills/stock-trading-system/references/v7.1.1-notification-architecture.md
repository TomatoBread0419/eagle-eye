# V7.1.1 Notification Architecture

**Date:** 2026-06-18
**Scope:** WeChat Delivery SLA for Eagle Eye

## Three-Tier Notification System

### Level 1: Heartbeat (hourly)
- `~/.hermes/scripts/eagle_heartbeat.py`
- Cron: `0 * * * *` (no_agent)
- Always delivers heartbeat to WeChat
- Tracks: DNS, API, Dashboard, orders, executor_success gap, scheduler activity
- New fields: `scheduler_last`, `executor_last`
- EXECUTOR_STALLED: executor_success gap > 90min → critical notification

### Level 2: Warning (≤60s)
- Events: ENTER_DEGRADED, EXIT_DEGRADED, TRADING_LOCK, DATA_STALE, API_FAILURE_SPIKE, WATCHDOG_ALERT
- Spool directory: `~/stock_trader/notifications/spool/warnings/`
- Relay: `~/.hermes/scripts/ops_notify_relay.py` (1min cron)
- Silent when no events — only delivers when spool has files

### Level 3: Critical (≤60s)
- Events: EMERGENCY_STOP, DATABASE_CORRUPT, SYSTEM_OFFLINE, EXECUTOR_CRASH
- Spool directory: `~/stock_trader/notifications/spool/critical/`
- Same relay as Level 2

## Architecture Pattern: Filesystem Spool → Cron Relay

This pattern enables near-real-time notification without a persistent daemon:

1. Event source writes JSON to spool directory
2. Relay cron (every 1min) reads spool, formats messages, outputs to stdout
3. no_agent cron delivers stdout to WeChat
4. Processed files moved to `spool/processed/` for audit

**Why this pattern on Termux/Android:**
- No persistent daemon needed (Android kills them)
- Survives crashes (spool files on disk)
- Dedup via filename hash prevents duplicate sends
- Escalation: >50 spooled files → WATCHDOG_ALERT

## SLA Rules

- 2 consecutive missed heartbeats → SYSTEM_OFFLINE
- Executor no success for 90min → EXECUTOR_STALLED
- Spool overflow (>50 files) → escalated to WATCHDOG_ALERT
- WeChat rate limit → cron_watchdog detects (5min)
